## What Nudge is
A personal follow-up agent built on Cloudflare's Agents SDK. The user chats in plain language ("remind me to pay rent on the 1st and keep nudging until I confirm", "follow up with Priya on Friday if I haven't heard back"). Nudge turns that into structured tasks, schedules reminders, and keeps following up on its own: re-nudging with growing urgency, honoring snoozes, and stopping only when the task is marked done. It is for any persona (students, parents, freelancers, managers). The differentiator from a normal reminder app is that it follows up autonomously and learns the user's habits.

## Hard requirements (this is a job assignment; all four must be clearly present)
1. LLM: Llama 3.3 on Workers AI (model id `@cf/meta/llama-3.3-70b-instruct-fp8-fast`) via the `AI` binding. No external API keys needed.
2. Workflow / coordination: the agent's scheduler (this.schedule) drives reminders, escalation and a daily briefing. Model the task lifecycle as an explicit state machine: pending -> nudged -> snoozed -> done (plus cancelled), with escalation levels gentle -> firm -> urgent.
3. User input: a streaming chat UI (React, served from the same Worker as static assets).
4. Memory / state: the agent's built-in SQL storage (this.sql) for tasks, an events log, and user preferences.

## Product behavior
Tools the LLM can call (define with zod schemas, server-side execution, following the starter's tool pattern):
- addTask(title, notes?, dueAt as ISO-8601 with offset, repeat? (none|daily|weekly|monthly), persistence (gentle|firm|urgent), maxNudges?)
- listTasks(filter? pending|snoozed|done|all)
- updateTask(id, fields)
- snoozeTask(id, minutes or until)
- completeTask(id)
- cancelTask(id)
- getBriefing() returns what is due today, overdue, and snoozed
- setPreferences(timezone?, quietHoursStart?, quietHoursEnd?, briefingTime?)

Autonomous behavior (this is the core):
- When a task's dueAt arrives, a scheduled callback checks the task is still pending/snoozed-expired. If so it posts a nudge message into the chat as an assistant message (persisted, so the user sees it when they return), writes an event, marks the task "nudged", and schedules the next nudge with exponential backoff (e.g. 15m, 1h, 3h, then daily) capped by maxNudges. Tone escalates with level: gentle (friendly), firm (direct), urgent (short and insistent). Nudge text should be generated by the LLM from a small prompt including the task, nudge count and tone, with a safe template fallback if the model call fails.
- Callbacks must be idempotent and must re-check state, so completed/cancelled tasks never get nudged, and deleting or completing a task cancels its pending schedules.
- Recurring tasks: on completion, create the next occurrence and schedule it.
- Quiet hours: nudges that fall inside quiet hours are deferred to the end of the window.
- Daily briefing: a cron-style schedule at the user's briefingTime posts a short summary message.
- Habit learning (simple, deterministic, no ML needed): log events (nudged, snoozed, completed, with timestamps). If the user usually snoozes a time-of-day bucket, or usually completes tasks within N minutes of a nudge, derive a suggestion and store it in preferences (e.g. preferredSnoozeMinutes, "mornings get snoozed"), and have the system prompt use it. Expose this in the UI as "What Nudge has learned".
- Time handling: the client sends its IANA timezone on connect; store it in preferences. Inject the current local date/time and timezone into the system prompt every turn so relative dates ("tomorrow 9am", "next Friday") resolve correctly. Validate that the model's dueAt is a real future ISO datetime; if not, have the tool return a clear error the model can recover from.

Data model (SQL tables created on first use, with migrations done idempotently in code): tasks (id, title, notes, due_at, repeat, persistence, status, nudge_count, max_nudges, snoozed_until, last_nudged_at, created_at, completed_at), events (id, task_id, type, at, meta), prefs (key, value).

## UI (React + Tailwind or the starter's styling; clean, modern, responsive, light/dark)
- Left/main: the streaming chat from the starter, with the agent's nudge messages visually distinct (small bell icon and tone badge).
- Right/side panel (collapsible on mobile): live Tasks list grouped by Overdue / Today / Upcoming / Snoozed / Done, each with a status chip, due time, nudge count, and quick actions (Done, Snooze 15m/1h/tomorrow, Cancel) that call the agent via @callable RPC methods (not by sending chat text). The panel updates live when state changes (use the SDK's state sync/broadcast or a refetch triggered by a websocket message).
- Browser Notification API: ask permission once, and when a nudge arrives while the tab is open/backgrounded, show a system notification. Also an in-app toast.
- An empty state with 3 example prompts the user can click.
- A small "What Nudge has learned" card.
- A "Reset my data" button (confirm dialog) that clears this agent's tasks/events/prefs.
- Identity: use a persistent anonymous user id in localStorage as the agent instance name so each browser gets its own agent, and document this as a deliberate simplification (no auth).

## Quality bar
- TypeScript strict, small focused modules (e.g. src/server.ts for the agent, src/lib/tasks.ts for pure task/state-machine/backoff/quiet-hours logic, src/lib/time.ts, src/tools.ts, client components under src/app or the starter's equivalent). Keep pure logic free of Cloudflare imports so it is testable.
- Add Vitest unit tests for the pure logic: state transitions, backoff schedule, quiet-hours deferral, recurrence date math, and dueAt validation. `npm test` must pass.
- `npm run typecheck` (or tsc --noEmit) and `npm run build` must pass. Run them, fix everything, and run `npm run dev` long enough to confirm the Worker starts without errors, then stop it.
- Handle errors gracefully (model failure, bad tool args, scheduling failure) with user-visible, friendly messages. No secrets in the repo.
- wrangler.jsonc: name "nudge", compatibility date current, nodejs_compat as the starter needs, AI binding, Durable Object binding(s) and migrations with new_sqlite_classes, static assets config as the starter does. It must deploy with `npx wrangler deploy` and also work with Cloudflare Workers Builds when the repo is connected from GitHub (build command `npm run build`, deploy command `npx wrangler deploy`). Do not deploy anything yourself.
